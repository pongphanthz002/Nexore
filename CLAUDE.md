# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Keep this file current.** Whenever a change to the system is finished (new feature, changed behavior or data flow, fixed known gap, new convention or gotcha), update the affected sections of this file in the same piece of work, before reporting it done. Remove statements the change made false; don't append a changelog.

## Commands

```bash
npm run dev     # Next.js dev server on :3000 (PWA/service worker disabled in dev)
npm run build   # Production build (generates the PWA service worker into public/)
npm start       # Serve the production build
npm run lint    # next lint (extends next/core-web-vitals)
npm test        # vitest run (src/**/*.test.ts); npm run test:watch for watch mode
```

Vitest (`vitest.config.mts`, `@/` alias) covers the pure logic in `src/lib` (`grade-calculation`, `timetable`, `attendance`, `class-stats`, `classroom-tools`, `feature-access`, `gacha-physics`); there are no component or Firestore tests. Verify changes with `npm test`, `npm run lint` (currently warning-free; keep it so), `npx tsc --noEmit`, and by exercising the UI. Effects that intentionally run only on specific changes carry an `eslint-disable-next-line react-hooks/exhaustive-deps` with a reason; loaders that only depend on `userAccount` are `useCallback`s. `public/sw.js` and other `public/` workbox files are build output from `@ducanh2912/next-pwa`; don't hand-edit them.

Dev server gotchas:
- `npm run build` and `npm run dev` share `.next/`. Building while the user's dev server runs corrupts it (404s, stale chunks), and editing `next.config.mjs` restarts it, possibly on another port if 3000 is held. After either, tell the user the URL to use, and suggest `rm -rf .next && npm run dev` if pages misbehave.
- A service worker left by a production run (`npm start`) serves stale bundles on localhost. In development `AuthContext` unregisters it and clears its caches automatically. If console logs don't match the current code, suspect this or a second `next dev` still holding the port.
- Sign-in needs the user's Google account, so Claude can't test signed-in flows itself. Ask the user to sign in (in the browser pane or their own browser) and share console output.

No `.env` is needed (`.env.example` is a leftover): school and teacher configs come from Firestore at runtime. Production builds strip `console.log` (`compiler.removeConsole` in `next.config.mjs`); use `console.error`/`warn` for anything that must survive. The Master Registry config is hardcoded in `src/config/master-registry.config.ts` (do not modify it casually — it points at the shared `nexore-hub` project).

Stack: Next.js 14 App Router, React 18, TypeScript (strict), Tailwind, Framer Motion, Firebase v10 client SDK, `exceljs`/`xlsx` for whitelist import/grade export. Path alias `@/*` → `src/*`. UI copy is primarily Thai.

## Architecture

Nexore is a **client-only, multi-tenant, multi-Firebase-project** app. There is no backend/API layer: every page talks to Firestore directly from the browser. Data is split across three tiers of separate Firebase projects, and the app connects to the right one at runtime using configs it reads from the tier above. `AGENTS.md` has the original data model and workflows. Where it disagrees with this file, the code and this file are current: Master Registry `users` is keyed by UID (not email), and student data fan-out uses `subjects.teacherId` (not `teacherNodes`).

1. **Master Registry** (`nexore-hub`, hardcoded): `users/{uid}` → `{email, schoolId, role, userId}` and `hubs/{schoolId}` → `schoolFirebaseConfig`. Legacy `users/{email}` docs are still read and migrated to `users/{uid}` on login (`firestoreService.getUserMapping`); admin-created accounts without a UID are written email-keyed until the owner logs in. Accessed via `firestore.service.ts`. Also the only Firebase Auth instance (Google sign-in).
2. **School DB** (one project per school): `teachers`, `students`, `admins`, `subjects`. Accessed via `school-database.service.ts`. Each teacher doc also stores that teacher's own `firebaseConfig` and optional `defaultRoom`. Subjects store slots as Thai day names + `"08:30-09:20"` ranges (`schedules`, up to 3; legacy `day`/`time`), plus optional `subjectCode` (the official code users see; `subjectId` stays the internal key) and `room` (empty = the teacher's `defaultRoom`).
3. **Teacher DB** (one project per teacher): `attendance` (one doc per session, all students' records), `attendanceSummaries/{subjectId}` (every session × student status of the subject, version 2 = always complete: `saveAttendance` merges into a v2 summary and otherwise rebuilds it from every session (`rebuildAttendanceSummary`), so a summary never covers only the sessions since it was created; missing or v1 summaries count as absent and are rebuilt by `getSubjectAttendance` (history view, per-student sheet), the teacher home loader and `ensureAttendanceSummary` when sessions are scanned), `gradeSummaries/{subjectId}` (per-student total/grade/pending assignment ids plus each assignment's due day, for the home dashboard; see Dashboard below), `gradeConfigs`, `assignments`, `assignmentGroups`, `studentScores` (doc id `${subjectId}_${classroom}_${studentId}`), keyed by `studentId`/`subjectId`. Accessed via `teacher-database.service.ts`. Every method takes the teacher's `firebaseConfig` as its first argument.

Student reads fan out: `student-database.service.ts` loads the student's subjects (`getSubjectsForStudent`: classroom query + `studentIds array-contains`), resolves the teachers of those subjects (`subjects.teacherId`, not `teacherNodes`), then queries each Teacher DB by `studentId` and merges results. Subject cards are one per teacher + name + code + classroom (so a basic and an additional subject with the same name stay apart, as in the teacher's picker); docs of the same subject split per period share a card whose `subjectIds` lists them all, and its grades (the score doc with the most entered) and attendance are read from every one. Attendance comes from each subject's summary doc (1 read); it falls back to scanning sessions when there is no complete summary yet. Grades read the subject's visible assignments, groups and grade config per score doc and use the shared grade calculation (see Grades below). Only teachers with a `uid` (registered) are queried and shown on the student subjects page (`isActiveTeacher`); the timetable shows every teacher's subjects. A registered teacher without their own `firebaseConfig` stores data in the School DB (the `firebaseConfig || schoolFirebaseConfig` fallback is intentional).

### Key mechanisms

- **`src/lib/firebase.ts` — `firebaseManager`**: caches `{app, auth, db}` per instance. Use `firebaseManager.getSchoolDb(config)` / `getTeacherDb(config)` — never `getFirestore()` or hand-built instance names. Both name instances `db-${projectId}`, so a teacher on the school DB shares one app. Teacher instances are capped (LRU, 15) and released with `deleteApp`; `clearAllInstances()` (sign out) keeps only the master. The module-level `db`/`auth` exports are the **Master Registry**, not a school DB.
- **`src/contexts/AuthContext.tsx`**: resolves uid → master mapping → hub (`getHubCached`, localStorage 24h) → `schoolDatabaseService.findMember` (doc read by `mapping.userId`, then uid query, then email query). Exposes `authStatus` (`ready` / `not-registered` / `not-in-whitelist` / `offline-error` / `error`); `LoginSignup` and `useIdentityCheck` route from it and must not re-query Firestore. The account is cached stale-while-revalidate (`NEXORE_USER_ACCOUNT`, shown immediately up to 7 days, re-checked in the background after 30 min; network failures keep the cached account). `setUserAccount` writes the cache; call `invalidateCache()` after changing a user's role/mapping. Set `setSignupValidation(true)` before a signup-time sign-out.
- **Read budget**: `src/lib/firestore-helpers.ts` provides `TtlCache`, `dedupe`, `withRetry`, `allowAction` (button cooldown), and `runPool` (bounded-concurrency loop that stops on the first thrown error; catch inside `fn` for best-effort work). `dedupe` keys are global, so give each call site a unique prefix (e.g. `hub:`, `user-mapping:`, `teacher-config:` — `getTeacherConfig` is deduped so the home timetable and statistics share one read). `TtlCache` scopes its own keys per instance, so different caches may reuse the same key such as `${projectId}:all`. School rosters/subjects are cached 5 min in `schoolDatabaseService` and invalidated by its own writes — pass `forceRefresh` only for explicit user refreshes. Per-student subject context is cached 5 min and the subjects overview 2 min in `studentDatabaseService`. `getAll*` (whole collections) is for admin roster screens and the teacher profile's elective picker only. Teacher screens use `getSubjectsForTeacher` + `getStudentsForSubjects`; the grades and attendance pages get them (plus the teacher record) from `useTeacherRoster` (`src/hooks/`), which shows a localStorage copy at once (`STORAGE_KEYS.TEACHER_ROSTER`, `src/lib/teacher-roster-cache.ts`: up to 7 days, re-read after 10 min, students trimmed to id/name/number/class/photoURL) and is cleared by every `schoolDatabaseService` invalidate (any School DB write from this device) and by sign-out; student screens use `getStudentForAccount`, `getSubjectsForStudent`, `getTeachersByIds`.
- **Dashboard** (teacher home below the timetable, `src/components/stats/TeacherDashboard.tsx`; logic in `src/lib/class-stats.ts`, loading in `src/services/teacher-stats.service.ts`): three cards over every subject the teacher teaches. Podium = top 3 by mean total over subjects with scores (`topScores`; name and class only). Pending = the 5 students with the most work that is due and still unscored, as lines over four weeks or month ends since May (`pendingTimeline`; due = deadline, else the day the assignment was created). Attendance = มา (incl. กิจกรรม) / สาย / ลา / ขาด (incl. หนี) share per room as overlapping areas for this week / month / term (`attendanceByRoom` over `sessionMixes`, year-less dates placed by `sessionDay`), the top room of each kind labelled on the chart. Pastel series colours are in `PASTEL` (checked for colour-blind separation on the light surface). Reads: 2 docs per subject (`gradeSummaries` + `attendanceSummaries`), cached in localStorage (`STORAGE_KEYS.TEACHER_STATS`, 10 min, versioned by `TEACHER_STATS_VERSION`, `src/lib/teacher-stats-cache.ts`); pulling down on the teacher home forces a re-read (`PullToRefresh`, 10 s cooldown); `saveGradeSummary` and `saveAttendance` clear the cache. The grades page writes the open subject's summary (`buildGradeSummary`, 2 s debounce, skipped when `gradeSummaryFingerprint` is unchanged). A subject with no summary of the current `GRADE_SUMMARY_VERSION` (3: rebuilt once because scores edited by older app versions left some stale) is built once by the home loader from its scores and saved (`buildSubjectGradeSummary`), and a subject with no complete attendance summary gets one from its sessions, so every subject shows. Summaries can lag when scores change outside the grades page; student deletes (`deleteAllStudentData`, `deleteSubjectStudentData`) remove the student from them. Charts are plain SVG measured to their container (no chart library), animated with Framer Motion and a reduced-motion fallback. Cards set their own text colour (`text-gray-900 dark:text-gray-50`): the teacher layout sets none and body text stays dark, so anything new under it must too.
- **Pull to refresh** (`src/components/PullToRefresh.tsx`): touch-only, mounted once per screen with an `onRefresh` that returns a promise; a raised knob under the header, the page doesn't move. Ignores pulls that start in a dialog, `input`/`select`/`textarea`, `[data-no-pull]` or while a popup locks scrolling. Used by the student subjects page and the teacher home dashboard instead of refresh buttons (they have no other manual refresh on desktop).
- **Offline banner** (`src/components/OfflineBanner.tsx`, in the root layout): a raised pill above the dock while `navigator` reports offline, then "กลับมาออนไลน์แล้ว" for 2.5 s. The grades page keeps its own save-status line for unsaved cells.
- **Notices and confirmations**: never `alert()` / `confirm()`. Results go through `toast.success` / `toast.error` / `toast.warn` / `toast` (`src/components/Toast.tsx`; `<Toaster />` in the root layout shows raised pills at the top, above popups, tap to dismiss, and they survive navigation). Yes/no questions use `await askConfirm({ title, message, confirmLabel, tone })` (`src/components/ConfirmHost.tsx`, `<ConfirmHost />` in the root layout, built on `ConfirmDialog`); use a page's own `ConfirmDialog` when it needs live content or a busy state. Form validation shows inside the form with `FormError` (`Modal.tsx`) above the buttons, cleared when the form opens: the subject forms (profile and admin), the admin teacher/student add and edit popups, and the School ID / ID steps of student and teacher setup (which show the School ID help as text under the field).
- **Loading skeletons** (`src/components/Skeleton.tsx`): `Bone` (sunk shape, `.skeleton` in `globals.css`, breathing, still under reduced motion), `SkeletonCard` (raised), `SkeletonRows` (list rows with photo / trailing pill), `SkeletonGroup` (one `role="status"` label). Every loading placeholder uses these (Suspense fallbacks too: full-screen ones use `LoadingScreen`; home timetable `TimetableSkeleton`, dashboard, student subjects, grades, attendance, admin rosters and tiles, profile subject list); don't add ad-hoc `animate-pulse` boxes or "กำลังโหลด..." text.

It portals to `<body>` at `z-[100]`, closes on Escape and backdrop (`dismissible={false}` while saving, `closeOnBackdrop={false}` for forms), locks page scroll, moves focus in (`data-autofocus`) and back, keeps showing the last content during its exit animation (so callers can clear state at once; still guard nullable content with `{x && (<>…</>)}`), and is a bottom sheet on phones with `sheet`. Menus that must open over a popup need `z-[110]` or higher (the profile subject menu does). Don't hand-build `fixed inset-0` overlays.
- **Profile photos** (`src/components/Avatar.tsx`): Google photo or the name's first letter (Thai titles skipped); a photo that fails to load falls back to the letter and logs `[avatar]` with `console.warn`. Own photo: `googlePhotoURL(user)` (`src/lib/google-photo.ts`, `photoURL` or the Google provider's, asked at 192 px). Others' photos: `resolveAccount` saves the Google photo to the member's teacher/student doc as `photoURL` (`savePhotoURL`, one write only when it changed, no cache invalidation), so a person shows up after they sign in. Shown on both profiles, the admin roster rows, the grades page's student sheet and the attendance check list (`photoURL` is kept in the trimmed roster cache).
- **Admin screens**: `/admin/dashboard` is the admin home: School ID (tap to copy), tiles for ครู / นักเรียน (total + registered share, registered = has `uid`) / วิชาเรียน / ระบบเพิ่มเติม (`/admin/dashboard/features`, see Feature access), and the danger zone (`src/components/admin/SchoolDangerZone.tsx`: reset data or delete the school after typing the school ID). `/admin/dashboard/users` only redirects there. An edit that removes students from a subject with data warns first, then `deleteSubjectStudentData`, as in the teacher profile.
- **Teacher profile** (`src/app/teacher/dashboard/profile/page.tsx`): identity card (Google photo or initial, role and ID chips; the pencil expands name, `defaultRoom` and, for admins, the teacher-ID link inline), "การสอน" card (subject hue chips, opens subject management), and "บัญชีและระบบ" rows (School ID copy, teacher DB → the Firebase Config popup).

- **Classroom tools** (teacher เพิ่มเติม → `/teacher/dashboard/additional/classroom`; logic in `src/lib/classroom-tools.ts`, UI in `src/components/classroom/`): opens on the period being taught now (every room of a merged period), otherwise the `SubjectPicker`; เปลี่ยนห้อง always. Two tabs: **สุ่มเรียก** is `GachaMachine`: capsules (photo or initial, no names) are bodies in a small position-based physics world (`src/lib/gacha-physics.ts`: gravity, drag, bouncy capsule/glass collisions, rolling spin, a stirring force while the crank turns, a hole at the bottom for released capsules; `TrayWorld` bounces the capsule in the catch tray), drawn by writing transforms each animation frame and idle once everything rests. - **Changing a teacher's DB** happens only in the teacher profile "Firebase Config" popup: `teacherDatabaseService.validateConfigShape` (format, appId/senderId/authDomain consistency, not nexore-hub or the school project) → `verifyConnection` (write/read/delete a doc in `_nexore_connection_check` on a throwaway app) → typed confirmation → `schoolDatabaseService.updateTeacherFirebaseConfig`. Save is disabled unless the form still matches the validated config. Existing data is not migrated.
- **Whitelist uploads** (Excel, admin pages under `src/app/admin/dashboard/users/{teachers,students,subjects}`) write with `merge: true` and only whitelist-owned fields (`name`, `class`, `number`, …). They must never write `email`/`uid`/`role`/`firebaseConfig` on existing docs, and `teacherNodes` only when the row provides it, so re-uploading keeps registered teachers' configs and accounts. `saveStudentWhitelist` returns `unknownTeacherIds` for the admin warning. Students and schools use the system live, so uploads must preserve existing data:
  - The `save*Whitelist` methods commit through `commitInBatches` (200 writes per batch, 4 batches in parallel, `withRetry`) and take an optional `onProgress(done, total)`. Excel cells are coerced with `String()` since IDs may parse as numbers.
  - Rows missing from the file are deleted (with their Teacher DB data) only after a confirmation dialog that lists them and flags registered (`uid`) users. Deletes run via `runPool` (students 5, teachers/subjects 3) and collect failures instead of aborting.
  - The subject sheet layout lives in `src/lib/subject-excel.ts` (`downloadSubjectSheet` builds a styled exceljs file, `parseSubjectRows` reads uploads): teacher ID, รหัสอ้างอิงระบบ (`subjectId`), รหัสวิชา, วิชา, ประเภท, ห้อง, ห้องที่สอน, วัน/เวลา/ชั่วโมง ×3, นักเรียน (elective student IDs). A column missing from the file leaves that field untouched (old "วัน/เวลา/จำนวนชั่วโมง" files update only the first slot); a present column overwrites, blank clears.
  - Rows match existing subjects by รหัสอ้างอิงระบบ first (so renamed subjects keep their data), then by `teacherId|subjectName|classroom` (whole classroom cell first, then each comma-separated room), and keep their `subjectId`, because Teacher DB data is keyed by it. Never regenerate IDs for existing subjects. `subjectType` is written only when the column is filled (new rows default to `basic`).
  - An ID-matched subject that already has data (`subjectHasData`) keeps its classroom and students even if the file changes them; the confirmation lists those, and electives the file leaves with no students.
  - Deleting a student (`studentDatabaseService.deleteStudentCompletely` → `teacherDatabaseService.deleteAllStudentData`) removes their scores, attendance-summary entries and rows in `attendance` session docs in every Teacher DB found via their subjects (sessions are searched in their current subjects plus every subject whose summary lists them).
  - Deleting a teacher whose `firebaseConfig` points at the school project never calls `deleteTeacherDatabase` (it would wipe every School-DB teacher's data).
  - `src/components/UploadProgressModal.tsx` is the blocking progress popup (steps, %, count, `beforeunload` warning). Pages skip their empty-list skeleton while `uploadProgress` is set, so the popup shows on a school's first upload.
- **Timetable** (`src/components/timetable/`, logic in `src/lib/timetable.ts`): one component for teachers and students (`TodayTimetable role=…`) on both dashboards. Home card = today's whole day on a vertical timeline (red now-line, current period ringed and raised while the others sit sunk, past periods slightly quieter but still stronger than any other day's (`past` vs `other` in `globals.css`), "วันนี้ไม่มีคาบ" + next period when empty). Tapping it opens `TimetableFullscreen`: one day per page, time left→right, opens on today, swipe (touch) / ‹ › + arrow keys (fine pointer) / day chips; today stays the most prominent day (its chip is always red, other days' periods use the quieter `other` block state, and a "กลับไปวันนี้" button shows on other days); a phone held upright (<768px) gets the view rotated 90° via CSS. Weekend days show only when they have periods. All days share one hour range (`weekRange`). Subject colours are palette B (`hueVars`, one hue per subject name). A teacher period taught to several rooms at the same time (same name, start and end) is one entry. Teachers get an attendance bar above the card from period start to end until every room of it is checked today; it and the current block's "เช็ค" button open the normal attendance page with `?mode=attendance&subjectIds=a,b&hours=n`.
- **Student subjects page** (`src/app/student/dashboard/subjects/page.tsx`, views in `src/components/StudentSubjectViews.tsx`): subject cards (1 column on phones, 2 from `md`, 3 from `xl`, inside `max-w-7xl` like the header) with hue bar, grade, total bar, and red only for overdue work or attendance under 80%; then a subject view with the hue header and คะแนน / เวลาเรียน tabs. The grades tab leads with the grade (big), total, the grade-scale ladder with points to the next grade (`StudentGradeInfo.scale`), and คะแนนเก็บ / กลางภาค / ปลายภาค tiles (`midtermEntered`/`finalEntered` tell an unentered exam from a 0); from `lg` it is a 12-column grid (grade card 5, tiles 7). - **Teacher subject picker** (`src/components/SubjectPicker.tsx`): the subject list of both the grades and attendance pages. "วันนี้" first (today's periods from `entriesForDay`, drawn as `timetable-block` past / current / upcoming via `periodState`, merged rooms in one block), then "ทุกวิชา": one card per subject name + code (`subjectGroups`) in its `buildHueMap` hue, with code, type and teaching room, and one chip per classroom with its student count. The history view's totals come from the subject's summary doc (`getSubjectAttendance` + `studentAttendanceTotals`, 1 read; sessions are scanned only when no summary exists) and load only in the history view, not while checking. Today's sessions (which periods are checked) load beside the subject list instead of before it. Statuses use the coloured, animated `AttendanceStatusSelect` dropdown (row tint follows the same hues). Opened from the home timetable, saving returns to the dashboard.
- **Teacher subject editing** (profile → "จัดการวิชาเรียนที่สอน"): all subjects in one card; right-click or press-and-hold (or the ContextMenu key) opens แก้ไข / ลบวิชา. The add form doubles as the edit form (name, code, type, classroom, teaching room, up to 3 slots, elective students). When an edit removes students (classroom change or elective list) and `teacherDatabaseService.subjectHasData` is true, a warning comes first, then `deleteSubjectStudentData` deletes those students' scores, session rows and summary entries for that subject. The profile card holds the teacher's `defaultRoom`.
- **Grades** (`src/app/teacher/dashboard/grades/page.tsx`): one Excel-like grid (`src/components/ScoreGrid.tsx`) for both view mode (read-only, groups folded to their scaled column) and edit mode ("กรอกคะแนน" … "เสร็จสิ้น"). Phones (<768px) get `MobileScoreEntry.tsx` in edit mode instead (one assignment at a time).
  - **All score math lives in `src/lib/grade-calculation.ts`** (`computeBreakdown`, `buildColumns`, `gradeFor`), used by the teacher grid, the per-student popup, the Excel export (`src/lib/grade-export.ts`) and `studentDatabaseService` so every screen shows the same numbers. Don't compute totals anywhere else. Rules: a missing score key/field means "not entered" (pending, counts as 0) while a stored 0 is a real score; hidden assignments never count; a group scales its visible assignments to `rawScore`; midterm/final are entered out of `gradeConfig.midtermMax`/`finalMax` (default = the proportion) and scaled to the proportion; collected over its proportion is flagged, not scaled.
  - Column order is `assignments.order` (normalized once on load for older data). A group's assignments render together where its first assignment is, under a merged header, with the scaled column at `assignmentGroups.scaledPosition` (unset = after the last assignment). Group membership is `assignment.groupId`; `group.assignmentIds` is kept in sync. Structural edits (group via header selection + right-click "ปรับคะแนน", reorder by dragging ⋮⋮ on fine-pointer devices, ungroup, delete) go through `normalizeStructure` + `persistStructure` in the page, which write only changed docs.
  - Score edits autosave through `useScoreAutosave` (`src/hooks/`): debounced, per-cell `teacherDatabaseService.saveScoreCells` (`merge: true`, `deleteField()` to clear), so two devices editing different cells don't overwrite each other. Failed writes are re-queued with backoff; `beforeunload` warns while anything is unsaved; "เสร็จสิ้น" flushes first. Queued cells carry their subject/classroom. Values outside 0…max stay red in the grid (`invalidCells`) and are never saved. Undo/redo (50 steps) replays cell edits through the same autosave.
  - Column headers: mouse click / Shift / Ctrl / drag selects, right-click opens the menu. Touch: tap selects one column, press-and-hold then slide selects a range (a non-passive `touchmove` listener stops scrolling meanwhile), press-and-hold on a selected column or a two-finger tap opens the menu; emulated mouse events within 800 ms of a touch are ignored. Menu actions ("ปรับคะแนน", hide/show, delete) apply to every selected column when the clicked one is selected.
  - The grid's keyboard input goes through a single real `<input>` that follows the active cell (needed for paste, IME and tablet on-screen keyboards); cells themselves aren't focusable.
  - Deleting assignments goes through `teacherDatabaseService.deleteAssignmentsWithScores` (after flushing autosave), which also removes their values from `studentScores.assignmentScores`.
  - New assignments are created in the assignment popup (toolbar "เพิ่มงาน" or the grid's "+ เพิ่มงาน" column) so the teacher fills in description and deadline too. Each grid cell gets one background class from `cellBg` (Tailwind can't order two `bg-*` classes), so add new cell states there.
  - The Excel export uses TH SarabunPSK 16 for every cell.
  - Tapping a student opens `src/components/StudentSubjectSheet.tsx`: exactly the student's own subject view (`SubjectHeader`, คะแนน / เวลาเรียน tabs, `GradesView`, `AttendanceView`, `AssignmentSheet` from `StudentSubjectViews.tsx`), built from the page's loaded scores with `buildStudentGradeInfo` (`src/lib/student-grade-info.ts`, also used by `studentDatabaseService`, so both screens show the same numbers); attendance is the subject's `attendanceSummaries` doc via `getSubjectAttendance` (1 read, cached 2 min; built from the sessions when missing).

### Conventions (from AGENTS.md)

- Files: `<name>.service.ts` for DB access/business logic; `.screen.tsx` for UI-only screens with no DB calls; folders PascalCase. In practice the repo uses kebab-case `*.service.ts` and `page.tsx` files that call services directly — follow the surrounding file.
- Storage keys live in `src/config/storage.keys.ts` (`STORAGE_KEYS`); add new keys there.
- Email/UID are never stored in Teacher DBs; `studentId` is the primary key there.
- Never fetch a whole collection and filter client-side for student-scoped data.

## Things to know before touching security or data

- `firestore-rules/` contains reference rules, but `master-registry.rules` and `school-database.rules` are `allow read, write: if true` ("temporarily for debugging"), and `teacher-database.rules` only covers `subjects` and `media`. Role/ownership is enforced only in client code. Don't assume server-side protection when reasoning about access, and don't loosen anything further.
- Service methods take a typed `FirebaseConfig` (`src/types/firebase.types.ts`), but nothing distinguishes school from teacher configs at the type level — passing the wrong tier's config silently reads the wrong project. `userAccount.schoolFirebaseConfig` is always the **school** config; a teacher's own DB comes from their teacher record.
- Teacher `firebaseConfig` is hidden in the admin UI but still stored on the teacher doc (students need it). Rate limiting is client-side only; Security Rules / App Check / auth on school and teacher projects are still to do.

## UI

**Theme (dark/light)** is the app's own setting, independent of the phone's dark mode. `ThemeProvider`/`useTheme()` (`src/contexts/ThemeContext.tsx`) owns it: `isDark`, `toggleTheme`, `setTheme`, saved in `STORAGE_KEYS.THEME` (default light), applied as `html.dark`, synced across tabs, and updating `<meta name="theme-color">`. `themeInitScript` (`src/config/theme.ts`, kept outside the client module so the server layout gets the real string) sets the class in `<head>` before first paint. Tailwind uses `darkMode: 'class'`, so `dark:` variants and `isDark ? … : …` both follow the toggle. Never use `prefers-color-scheme` or a per-page theme state. `globals.css` pins `color-scheme: light` and keeps body text dark (pages set their own dark-mode text colours); the body backdrop is the soft-UI surface of the current theme. Dark mode is a warm charcoal (`--surface: 37 36 35`), not blue-grey, with its own shadow composites in `globals.css`: the light edge is short and faint (a wide one reads as a grey haze), so don't copy the light-mode offsets into dark, and Tailwind `gray-*` are theme-aware (`--gray-*` triplets in `globals.css`: Tailwind's greys in light, warm neutrals in dark), so a `dark:text-gray-400` is warm too; don't reintroduce `slate`/blue-tinted dark colours. Login, signup, role selection, setup and the loading screen follow the theme like every other page (their primary button is `bg-gray-900 text-white dark:bg-gray-50 dark:text-gray-900` with `rounded-xl shadow-neu-sm`; the Google logo sits on a white badge). `ThemeToggle` (in every header) is a `role="switch"` button keeping its illustrated look (blue sky with drifting clouds and a yellow sun, night with stars and a cratered moon; the orb can also be dragged) under a sunk inset rim.

**Soft UI (neumorphism)** is the look of every screen: page, cards and controls share one surface colour and get depth only from two shadows (light top-left, dark bottom-right). Tokens live in `globals.css` (`--surface` as an RGB triplet, `--neu-lo`/`--neu-hi`, composites re-declared on `:root, html.dark`) and Tailwind exposes them as `bg-surface`, `shadow-neu-lg` / `shadow-neu` / `shadow-neu-sm` (raised) and `shadow-neu-in` / `shadow-neu-in-sm` / `shadow-neu-in-xs` (sunk). Rules: big cards rise (`bg-surface shadow-neu-lg`, or `shadow-neu` in tight grids, with `gap-4`+ so shadows don't collide); small cards, tiles, wells, list rows and inputs sink (`shadow-neu-in-sm`, inputs keep a `border border-transparent` so focus borders still show); progress tracks use `shadow-neu-in-xs`; buttons rise and press in (`bg-surface shadow-neu-sm active:shadow-neu-in-sm`); a selected option is a raised knob in a sunk groove (dashboard/student tabs, the dock); the running period rises out of the timetable while the others sit sunk. Colours stay as before (subject hues, pastel chart series, Nexore red for warnings and the active dock item); only depth changed. `gray-500` is darker than Tailwind's in light mode (`--gray-500`) so grey text keeps 4.5:1 on the surface; small red text on the surface uses `red-700` in light mode. Popups (`Modal`) use `bg-surface` with a plain drop shadow (a light neu highlight reads as a halo over the dimmed backdrop). `ScoreGrid` stays a flat sheet with opaque sticky headers (`headBg`, kept in step with the surface). `THEME_COLORS` (status bar, and the dark mix colour of timetable blocks in `hueVars`) equals the surface colours. Chart SVGs that need the page colour (dot outlines) use `THEME_COLORS`.

`SKILLS.md` is an older "Liquid Glass" UI guide (glassmorphism via backdrop-blur); the soft UI above replaces it, so don't add glass. The app font is Noto Sans Thai (`next/font`, Thai + Latin, `--font-sans` = Tailwind `font-sans`). The timetable, attendance page, subject editing and student subjects page follow the "taste" app rules on top of the soft UI: no glass/gradients, colour on data (subject hues, attendance statuses), motion only as transform/opacity with `useReducedMotion` fallbacks. The app is a PWA used on phones (iOS Safari edge-swipe-back is suppressed globally in `AuthContext` by cancelling `touchstart` in the left 24px, except on controls: cancelling `touchstart` also cancels the click, which is what made edge buttons ignore taps; controls get `touch-action: manipulation` in `globals.css`; `TeacherDock`/`StudentFooter` are thin wrappers over `src/components/NavDock.tsx`, which prefetches its routes and highlights the tapped item at once, since `router.push` does not prefetch; the dock is a raised bar with a sunk groove where the open item is a raised knob that springs between items (icon `text-red-600`, label `text-red-700`, `dark:text-red-400`); pages with a dock use `bg-surface` and about `pb-32` of bottom padding), so keep layouts mobile-first.
